## 错误、管道和结果统计

追踪关键命令的返回码由谁取得、是否被覆盖、是否在最终退出中保留。

- `set -e` 不是完整错误处理。检查函数作为 `if`、`!`、`&&`、`||` 条件执行时的上下文，以及子 shell、命令替换、后台任务中的失败传播；依据目标 shell 判断，避免跨解释器套用规则。
- `local value=$(command)` 等声明可能遮蔽命令替换的状态。`ERR` trap 的继承与触发也有条件，不能仅因存在 trap 就认定所有错误都会报告。
- 查询可能区分“匹配”“未匹配”“执行失败”等结果。按命令及选项核对返回码含义，不要把所有非零状态都解释成业务条件不成立；使用 `!` 时注意取得的是取反后的状态。
- 管道末端成功可能覆盖前面失败；检查 `pipefail` 或等价的显式状态处理。后台进程需要有对应的 `wait`；把日志送给 `tee` 或 `cat` 不代表已经收集到被测命令的状态。
- 对预期失败的用例，确认断言失败本身不会也被吞掉。检查计数器更新位置、被跳过的用例、提前退出和成功横幅。
- 分别核对仅清理失败、主体与清理同时失败时的退出状态。主体已失败时保留根本错误，清理错误作为附加诊断；主体成功但必要清理失败时不应无条件报告整套成功。

## 输出与诊断

把从入口到退出的帮助、阶段信息、动作和结果作为使用者可观察的契约审视。先区分供人阅读的报告和供程序消费的数据，再按实际调用场景判断格式与通道是否合适；格式偏好与正确性问题分别报告。

- **全流程与退出路径**：沿帮助、参数解析、初始化与预检、主要操作、校验与清理等实际存在的路径检查反馈，留意统一报告机制启用前的提前退出或中断。按副作用边界判断失败报告是否足以说明已完成的工作、文件或资源的改动及后续步骤是否执行；不能仅因未进入主操作阶段就声称没有改动。
- **分组与顺序**：按职责或执行阶段检查相关信息是否连贯。脚本提示与外部命令输出是否互相割裂，计划与执行消息是否各有用途、含义清楚；不能为了输出排版改变必要检查和操作的执行顺序。
- **信息角色与阅读负担**：区分命令来源、执行阶段、具体动作、错误原因、修复建议与整体结果，检查标题和前缀是否让使用者误判当前阶段，例如把命令名误读为正在执行的操作。按故障定位需要安排重点，避免重复帮助或背景信息淹没关键错误及下一步；前缀和篇幅由调用场景决定。
- **模式语义**：若支持 dry-run、apply 或无变化路径，检查同一动作的命名、时态及模拟提示是否一致。预览不能暗示副作用已完成，无变化不能误报新建；一致性不要求抹平各模式的真实差异。
- **阶段状态与报告时机**：判断现有标题、动作结果或汇总是否足以辨认相关阶段的未开始、进行中、完成与失败，而不只核对已有完成提示。是否补充独立完成提示，取决于信息缺口、流程长度、输出用途与阅读成本，不要求每个阶段固定增加成功日志。阶段成功应在对应必要操作、校验与清理完成后发出，整体成功应涵盖全流程的必要校验与清理；失败信息应定位阶段、保留根本原因，并区分已完成步骤与整体结果。
- **输出通道**：核对脚本自身与外部命令的 stdout、stderr 分工，以及帮助、数据、进度与错误的消费方式。涉及通道契约时分别捕获两路输出，并检查合并场景；只看终端合并显示可能漏掉重定向后标题与正文分离、信息丢失或数据被日志污染的问题。
- **修改后的验证**：输出或捕获方式变化时，按[断言与失败定位](#断言与失败定位)核对相关断言。若阶段结果属于输出契约，验证其出现次数、顺序与实际完成步骤一致，并按风险覆盖正常、失败、中断或清理失败的相关分支。涉及重定向、管道或 trap 时，同时核对退出码、信号处理、文件状态与资源清理；日志文本符合预期不足以证明这些行为未变。

## 信号与资源生命周期

先画出实际进程关系和资源所有者：测试入口、被测脚本、替身、管道中的日志进程，以及临时目录。存在子进程时检查先停止和回收进程，再删除仍可能被写入的夹具。

按契约区分正常结束、普通错误、初始化中途失败、清理失败和可捕获信号。仅有 `EXIT` trap 不足以证明所有中断路径都正确；也不要要求捕获 `SIGKILL`。

需要复现信号问题时：

1. 在自有临时环境启动受控进程；用检查点、就绪文件或其他握手确认到达目标阶段，避免依赖猜测性的固定 sleep。
2. 区分只向入口 PID 发信号与向整个自有进程组发信号。两种投递范围不是同一项验证；异步启动的 shell 还可能继承忽略的信号状态。
3. 记录退出状态、收到信号的范围、必要的清理日志、子进程和暂存文件是否残留；需要重试的契约还应检查重试结果。
4. 使用有期限的等待和退出处理。只有确认进程组由本次复现创建且仍受控时，才对其发组信号；不要使用广泛的进程名匹配终止命令。

关注三个容易遗漏的窗口：资源已创建但尚未登记；主进程退出但后代仍运行；日志接收端先被终止，导致清理输出遭遇 `SIGPIPE`。修复应针对实际窗口，不要求所有脚本都引入进程组管理器。

## 断言、替身和回归探针

### 断言与失败定位

检查正常路径、冲突保护、幂等性、恢复和重要边界，按风险判断覆盖是否充分，不以用例数量代替判断。

逐项核对“用例名称 → 真正执行的路径 → 观察到的事实”。`退出码非零` 加 `未打印成功` 通常不足以证明指定阶段的保护逻辑生效：可能在依赖检查或更早阶段就失败了。

| 宣称验证的契约 | 需要的关键证据 |
| --- | --- |
| 无效参数不产生写入 | 实际默认或显式目标、关联配置与源文件的必要状态不变 |
| 冲突保护 | 冲突对象内容或链接不被破坏，其他副作用符合约定 |
| 幂等性 | 重复运行后的结果及必要元数据符合契约，而非仅再次返回零 |
| 故障发生在指定阶段 | 阶段检查点、对应状态或稳定诊断能排除更早的失败 |
| 失败清理与恢复 | 暂存物、子进程和已完成步骤状态符合约定，必要时重试成功 |

断言观察对象必须与执行参数及捕获方式一致。预先创建但未被脚本使用的空目录不能证明默认 HOME 未被写入。快照应覆盖相关内容、类型、链接目标和契约要求的元数据；通常不比较会因读取改变的 atime，明确时间精度等限制。

调整 stdout、stderr 或日志捕获方式后，逐项核对相关断言，尤其是“不包含某文本”的否定断言：若仍检查与目标输出无关的通道或空日志，断言可能始终通过，应确认承载目标输出的通道确实被断言覆盖。

失败诊断应能关联用例、执行阶段、预期与实际结果及有用日志。尽量保留每次调用的日志上下文，防止重试覆盖首次失败证据。断言外的夹具或辅助函数失败也应可定位，且诊断命令自身不能掩盖原退出码。

### 替身边界

替身只控制测试需要的故障或边界，保留相关参数、输出、返回码和副作用语义。需要调用真实命令时提前保存可信路径，防止替身递归调用自身。检查替身是否确实命中、平台或路径匹配条件是否脆弱、故障是在预期操作之前还是之后发生。

保留足够的真实命令路径以验证集成契约；替身测试解释故障处理，真实命令测试解释实际集成，二者不能相互冒充。不要精确锁定与契约无关的调用次数、实现步骤或完整日志文本。若要区分失败阶段，选择稳定的诊断或可观察状态。

### 回归探针

怀疑测试误报通过时，用单点回归验证其检出能力：

1. 在独立临时副本中确认原基线通过。
2. 只引入一个针对目标契约的变体。例如向实际默认目标写入意外文件、移除某个早期失败分支的暂存清理，或让“最终校验失败”替身提前退出。
3. 用直接执行、日志或状态证据确认变体在目标场景中确实破坏了契约。文本修改成功或删除保护分支不等于回归生效；变体未产生预期行为变化时，不能把测试仍通过解释为覆盖缺口。
4. 检查原测试是否检出已生效的回归，以及失败是否来自预期断言。增强测试后，用同一探针确认检出能力。

探针证明的是测试能力或缺口，不代表当前被测代码存在同一缺陷。无需为每次审视建立完整变异测试框架，也不要求把探针永久保留为测试设施。

## 环境、路径和文件隔离

列出真实写入和外部读取的来源，再决定隔离范围。按脚本用途考虑 HOME、XDG 目录、当前工作目录、临时目录、PATH、CDPATH、locale、umask、shell 启动文件及 Git 等工具的环境变量与配置。环境清理不应意外换掉要验证的解释器或关键命令。

临时 HOME 无法阻止硬编码绝对路径、向源仓库写入或访问外部服务。存在这些行为时使用适当的副本、沙箱或命令边界替身；保留契约需要的配置，避免为“隔离”删掉真正要验证的输入。

- 使用归属明确的临时根目录，保留所需源树结构和符号链接语义。清理只删除本次拥有的路径，不能依赖空变量、无界通配符或可变工作目录。
- 应用程序的版本、帮助等辅助查询也可能初始化日志或缓存。根据实际行为隔离其工作目录、HOME 或其他写入位置，不能仅凭查询用途认定没有副作用。
- 检查复制或写入目标是否已经是符号链接，避免沿着链接改到真实命令或源文件；不要把“路径位于临时根下”等同于“解析后的目标也位于其中”。
- 区分逻辑路径和物理路径。`mktemp` 返回路径的父目录可能包含链接，而被测脚本可能使用 `pwd -P`。当这影响断言或替身匹配时，在临时目录建立别名复现，无需改动系统 `/tmp`。
- 按声明的输入范围检查相对与绝对路径、空格、尾部斜杠、链接入口、断链和不同工作目录。受控夹具不含换行可以是设计取舍，不必因此要求通用文件名序列化框架。
- 核对环境变量、当前目录、后台进程及临时文件是否在用例间泄漏。连续场景有意复用状态时应注释其依赖，独立场景则应明确重置。

## 兼容性与验证层级

先确认项目真正承诺的 shell 和系统。检查语法、内建命令、外部工具选项及文件系统行为；不要凭扩展名认定解释器，也不要把开发机 Bash 的通过当作较旧 Bash 的验证。

| 层级 | 可以支持的结论 | 仍不能证明 |
| --- | --- | --- |
| 静态阅读、语法或 lint 检查 | 所用检查器可识别范围内的结果 | 完整执行语义、异常路径与原生平台行为 |
| 当前系统的真实执行 | 记录的系统、解释器和工具组合下的行为 | 未运行的平台或版本 |
| 模拟 `uname` 或命令替身 | 特定分支选择及受控故障处理 | 被模拟系统的原生命令、文件系统和信号行为 |
| 目标解释器在另一系统执行 | 该解释器在该宿主上的运行证据 | 目标操作系统整体兼容性 |
| 目标系统原生执行 | 实际记录的平台与解释器组合 | 未覆盖版本、场景或配置 |

例如 Bash 3.2 支持声明需要关注较新数组、展开、内建选项等特性；GNU 与 BSD 工具还可能在 `stat`、`readlink`、`mktemp`、`cp`、`sed` 和 `ps` 上有差异。发现具体疑点后查实际命令帮助、目标版本文档或最小实验，避免凭记忆提出兼容性缺陷。

追踪解释器从测试入口到被测脚本及替身的完整链路。调用入口使用指定 Bash，但内部再次按 PATH 找到另一 Bash，会削弱版本验证结论；确认契约是沿用当前解释器还是验证 shebang 的选择，再判断实现对错。

结果写成“Linux 上真实命令通过；Darwin 分支以模拟 uname 覆盖；macOS 原生 Bash 3.2 尚未执行”一类可复核陈述，并替换为本轮实际组合。跳过、工具缺失和运行受阻分别列明，不计入通过。

## 整体结构与维护

### 目录与内容归属

从使用者需要调用的命令理解目录：公开入口能否被辨认，私有实现是否容易误作独立命令，子目录名称和层次是否对应稳定职责。多个独立用途的入口可以并存。

把文件里的内容与所属职责对照，追踪谁维护、谁消费、何种变动需要同步修改。代码、安装清单、文档和测试都可能存在重复定义或职责错位，不能仅凭扩展名或所在目录判定归属：

- **事实与策略**：共享布局或路径事实可集中，调用方的拒绝操作、诊断等级、适用平台和检查时机仍可能不同。不要为共享数据连带合并整套策略。
- **重复事实与相关事实**：同一事实的多份定义容易漏改；最低兼容版本、固定下载版本和平台包名等相关信息则回答不同问题，应明确对应关系，不能仅因都涉及同一工具就合成大清单。测试的独立预期也不应为去重而从被测结果推导。
- **文档与实现说明**：按读者、使用入口和独立维护边界决定 README 的位置与数量，避免每建子目录就复制一份，也不规定全仓库只能有一份。操作说明、完整参数帮助、清单数据和局部算法解释各有适合的位置；集中说明时用链接导航，避免维护多份同义正文。

### 职责与复用

按职责和调用阶段横向比较主脚本，覆盖新旧实现，主动查找分散的同类检查、重复规则、重复计算的稳定路径和重叠职责，不能只检查新增代码或测试设施。候选合并需要比较输入、前置条件、返回码含义、诊断、副作用及执行时机，而不只是比较文本：

- **同一规则的多份实现**：旧函数与新函数可能已覆盖同一类检查。优先评估复用现有能力，保留调用方特有的提示或处理顺序；职责合并后，名称、调用位置和导航也要反映当前用途。
- **相似操作的不同语义**：同一命令用于能力探测和业务查询时，返回码解释可能不同。若合并需要大量模式参数或分支才能保持契约，分别保留往往更清楚。
- **同一检查的不同时间点**：前置检查、写入前复查和最终校验可能保护不同状态窗口。可以复用检查实现，但不能因看似重复就删除必要的调用，也不能以早期结果代替对可变状态的重新读取。
- **稳定事实与动态状态**：多处复用的派生路径、规则列表或参数来源适合集中定义，避免后续修改漏改；仅集中有实际复用价值的内容，明确变量作用域与初始化时机，不为减少传参扩大共享状态。
- **函数数量与职责边界**：一个函数即使只有一个调用方，也可能清晰封装原子操作、资源归属或错误处理。不要按调用次数决定内联；合并职责重叠的函数，也要保留有独立行为契约的边界。

单个简单表达式的重复未必值得新增抽象。合并后核对原有诊断、退出状态、执行顺序与保护时机是否保留；有意改变的行为应单独说明和验证。

### 文件规模与状态归属

分别判断函数是否承担多个独立阶段、文件内职责是否连贯、目录是否引入多余层次。长文件可能主要由清晰独立的检查或测试场景构成；短文件也可能散布同一规则。先评估文件内函数、顺序与导航是否足够，不按固定行数切割，也不为减少文件数合并不同的生命周期。

当入口调度、资源操作、应用适配或夹具与断言等职责已形成边界时，比较拆分前后一次操作、故障定位或用例需要追踪多少文件，状态在哪初始化，谁拥有 trap、计数和清理。大型 heredoc 内嵌程序可成为独立文件的候选，以便原生检查和维护；短小局部的夹具或紧密连续的场景可保留在一起。

决定拆分时，说明文件职责、调用或 source 关系、接口、初始化与清理归属，以及允许共享的状态。明确 source 文件是否只定义函数或数据，加载时如有副作用则必须有理由；避免只移动代码却把原本局部的依赖变成隐式跨文件状态。

拆分后公开入口仍应清晰，保持工作目录独立性、执行顺序、日志与退出行为。实施较大拆分时，尽可能先验证机械移动保持原用例行为，再进行修复和新增覆盖，便于归因；不要求额外提交或固定文件数量。

### 语言分工与一致性

对辅助程序的语言选择，比较原生运行时接口或标准库带来的收益与安装依赖、跨语言参数和输出协议、故障定位及验证成本。确认解释器在被调用阶段已可用，尤其是安装或引导流程的早期阶段。采用多种语言不自动代表过度设计；为统一语言改写原生接口或引入长内嵌程序也可能增加成本。结构化清单与包管理器原生声明按其数据用途判断。

横向比较同一语言的命名、引用、函数组织和注释约定，以及各入口参数、报告和退出状态的同义约定。代码风格、接口契约与业务策略分别判断：沿用项目和语言惯例，统一有相同含义的约定，保留部署、诊断、安装等用途所需的差异。具体输出通道按[输出与诊断](#输出与诊断)核对。

### 方案自身复核

对拟议结构使用与现有代码相同的维护标准。选择能区分方案优劣的一两个真实维护任务，例如增加一个检查或修改默认路径，推演需要修改的文件、事实定义位置、执行链路和故障定位路径，并与维持现状或文件内整理比较。推演支持维护取舍，不能替代行为验证；简单局部修改不必另做完整架构分析。

新增文件、目录、README、公共接口或语言依赖应有具体收益，并说明合并后哪些旧定义会删除、哪些边界有意保留。把正确性修复、测试夹具和辅助设施增加的复杂度计入最终方案，避免为了简化生产入口把成本转移到更难维护的支持层。不为假设的未来扩展引入通用框架，也不把某次选择的目录结构、文档数量或语言组合固化为普遍规则。

### 注释与导航

注释应解释目的、特殊路径夹具、异步握手或真实命令转发的原因。删除过时、重复或复述代码的注释。

长文件可按职责设置一级导航、按场景设置二级导航，避免给每段机械编号。导航应反映实际结构，例如环境准备、断言设施、正常部署、冲突、故障恢复、汇总清理；具体划分由文件决定。
