# Shell 脚本交付审视

把脚本及其相关辅助程序、清单、文档和测试作为要持续使用和维护的交付产物审视。以当前代码、行为契约和可复核验证为依据，同时评估行为正确性、整体结构与维护成本，提出与问题规模相称的调整。

## 1. 确定范围与授权

- 从当前请求和会话中确定主审文件、关联脚本、目标平台与解释器、需要保持现状的文件，以及用户要审视方案还是直接修复。范围有实质歧义时先推进不依赖答案的工作。
- 仅审视时保持仓库文件不变，复现和试改使用临时副本；已经授权实施时继续完成修复与验收，不重复索要确认。
- 遵守适用的仓库约定，记录已有工作区变更，不覆盖用户工作。修改范围和兼容要求以本次任务为准，不继承其他任务的决定。

## 2. 完整阅读，建立结构与契约对应关系

审视目录或多个关联入口时，先辨认公开命令、私有实现、调用关系和目录职责，并纳入相关清单、文档与测试的内容归属。逐文件阅读后仍须横向比较，不能把各入口分别通过审查当作整体结构合理；新增顺序用于理解演化，不决定最终结构。单点审视只追踪与该问题相关的边界。

完整阅读主审文件，并追踪会影响行为的被调用或被 source 文件、相关配置、测试和执行入口。长文件分段读完，搜索结果不能代替完整阅读；无需扩展为全仓库无关审计。以当前代码为准，未经核对的历史测试结果只作为线索。

梳理输入与前置条件、执行阶段、文件或外部副作用、退出码与输出、失败后的状态及重试行为。涉及测试时，把重要契约对应到具体夹具、执行命令和断言；复杂时用简表记录“行为契约 → 执行路径与夹具 → 观察对象与断言 → 证据或缺口”。

区分使用者可观察的契约和内部实现。失败后保留已完成步骤、随后可重试，可能是合理设计；不要自行把“恢复”解释成必须全量回滚。

## 3. 按方向审视，判断调整收益

完整审视时覆盖下列六个方向，并阅读所链接的参考章节；专项审视只需阅读相关章节。按实际契约选择检查和实验，不把每个例子都当作必须支持的场景。

| 方向 | 核心问题 | 取证参考 |
| --- | --- | --- |
| 流程与生命周期 | 操作顺序、资源归属、失败传播与结果统计是否一致；整体成功是否涵盖必要清理 | [错误与统计](references/review-lenses.md#错误管道和结果统计)、[信号与资源](references/review-lenses.md#信号与资源生命周期) |
| 输出与诊断 | 全流程及退出路径的反馈是否充分，阶段状态、信息含义、时机与通道是否准确，关键信息是否易于定位 | [输出与诊断](references/review-lenses.md#输出与诊断) |
| 测试有效性 | 用例是否到达所声称的路径，断言是否观察正确对象并排除更早失败；关键风险是否有覆盖 | [断言、替身和回归探针](references/review-lenses.md#断言替身和回归探针) |
| 隔离与兼容性 | 读写位置、外部配置与命令来源是否受控；验证是否使用声明的解释器与平台 | [环境与路径](references/review-lenses.md#环境路径和文件隔离)、[验证层级](references/review-lenses.md#兼容性与验证层级) |
| 结构与维护 | 入口、目录和内容归属是否清晰；文件组织、规模、语言分工与复用能否降低整体维护成本 | [整体结构与维护](references/review-lenses.md#整体结构与维护) |
| 注释与导航 | 注释是否解释目的、特殊夹具与处理理由，导航是否反映实际职责和场景 | [注释与导航](references/review-lenses.md#注释与导航) |

结构判断先比较维持现状、文件内整理、职责合并和稳定规则集中，再考虑新增抽象与文件拆分。结合函数、文件和目录三个层次，比较修改点、阅读路径、共享状态与依赖成本；行数、文件数和语言数只作为线索，不设统一的数量目标。

## 4. 以可复核证据验证

1. 先确认运行入口和副作用已被隔离，再执行现有测试。必要时使用保留所需仓库结构的临时副本；仅更改 HOME 不代表已隔离全部写入。
2. 按实际语言和项目约定运行语法、静态分析和格式检查。通常包括适用解释器的语法检查、ShellCheck 与 shfmt 的只读检查模式；沿用项目参数，不擅自格式化。工具缺失时如实记录，不能记为通过。
3. 记录实际系统、解释器路径与版本、关键命令版本、命令及退出码、测试计数与跳过项。保留足够日志支撑结论；获取返回码时避免被管道或后续命令覆盖。
4. 对具体疑点做最小复现；怀疑测试误报通过时，按[回归探针流程](references/review-lenses.md#回归探针)验证测试的检出能力。无法运行时给出静态推导和未验证条件，不编造动态证据。
5. 核对测试确实执行、日志与退出状态一致、临时资源和自有子进程已清理；只读审视结束时确认受保护文件没有变化。

同一会话内复用已有验证时，先核对代码、相关输入和环境是否仍适用，并区分此前证据与本轮新执行的检查。代码变化、失败或新疑点需要相应验证；仅调整审视文字不必重跑已通过且仍适用的整套检查。

## 5. 形成结论，完成交付

按用户语言先给出“当前无需修改 / 需要小幅调整 / 应该重构”的结论及依据。重要程度依据实际影响和发生条件，不能把所有兼容疑点都列为高优先级。

每个值得报告的问题交代**类别、所属文件和位置、触发条件、影响、证据、建议**，明确属于测试脚本还是被测脚本。相关文件可交叉引用，按问题规模组织表述。

| 类别 | 表述标准 |
| --- | --- |
| 已证实缺陷 | 当前实现违背契约；说明是动态复现还是可确定的静态证据 |
| 测试覆盖缺口 | 某项承诺没有充分断言，或具体回归未被测试检出 |
| 合理设计取舍 | 说明收益、约束和适用边界，不包装成必须修复的问题 |
| 风格或维护建议 | 说明对阅读、定位或后续修改的收益，与正确性问题分开 |

未证实疑点单列为待验证事项，不混入已证实缺陷。不要为了凑清单而提出无关或低价值修改。

需要调整时，汇总正确性修复与有收益的维护调整，说明修改范围、拟采用结构、要补充或调整的断言与场景、验收方式。对容易误判为冗余而决定保留的关键检查或函数边界，简述依据。

提交结构调整方案前，按[方案自身复核](references/review-lenses.md#方案自身复核)检查新增边界和依赖的具体收益，并计入修复及测试设施带来的维护成本。

仅审视的任务到方案为止；已获授权的任务继续落实方案，检查受影响文件与入口，执行必要回归并核对范围。实施较大拆分时按[文件规模与状态归属](references/review-lenses.md#文件规模与状态归属)验证行为保持。无需为纯注释等低影响修改编写无价值测试。

交付时说明实际变化、本轮完成的检查、复用的证据和仍未验证的内容，尤其是平台与解释器组合。无需修改时也说明证据范围和剩余边界。
