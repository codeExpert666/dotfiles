# 开发后代码与文档整理

把已完成功能整理为行为清楚、结构可维护、使用文档连贯且验证范围明确的交付结果。
完整流程先审视代码，再按最终行为整理文档，最后验证；用户只要求其中一部分时执行对应阶段。
没有值得修改的问题也是有效结论，不为减少行数或产生变更而重构。

## 确定本次范围

- 从请求、既有授权和仓库约定中确定对象、支持的平台／版本、需保持的行为，以及“只审视”还是“审视并调整”。仅审视时不改源码和文档；已授权调整时完成实施与验证，不把每一阶段变成新的审批点。
- 记录工作区与暂存区已有修改，区分当前任务与用户工作。按仓库要求和变更风险保存必要的修改前副本或摘要；不以 reset、clean 或 stash 代替保留现场。
- 继承项目的状态、运行环境和发布约束。项目名称、账户、固定版本、截止日期、测试命令和目录布局都从当前项目核对，不从技能或上一次任务复制。
- 阅读范围以用户目标为界：整体审视覆盖公共入口、核心实现、相关配置／测试／交付清单及使用文档；专项审视只追踪必要依赖，不自动扩为全仓库改造。

## 审视并整理代码

开始代码阶段时读取[代码审视要点](references/code-review.md)。完整阅读范围内的文件，搜索结果只能帮助定位，不能代替阅读全文；再横向比较入口、模块和测试之间的职责。

为拟修改项建立“触发条件 → 现有行为与契约 → 实际影响 → 证据 → 最小调整”的对应关系，区分：

- 已证实的行为缺陷或测试覆盖缺口。
- 有具体维护收益的重复实现、死代码或过期兼容分支。
- 仍有用途的平台适配、防御检查、失败恢复和公开接口。

先比较保留现状、局部整理、合并职责和集中稳定规则的成本，再决定是否新增抽象或拆文件。
兼容分支的删除依据当前支持范围和真实调用方；证据不足时保留并说明疑点，继续其他可完成的工作。
只有兼容范围的实质选择阻塞后续工作时才向用户澄清，不自行宣布某个平台或格式退役。

保持最终行为、调用方、打包／安装映射、测试与必要说明一致。结构调整后重读保存的核心文件和入口；
涉及安装布局时，验证交付目录中的独立运行，避免开发环境搜索路径掩盖依赖缺失。

## 重编排面向使用者的文档

开始文档阶段时读取[文档审视要点](references/docs-review.md)。完整阅读相关用户文档，再核对命令帮助、配置示例和必要实现；只整理文档时无需启动代码全面清理。

先判断每类信息应由哪一页或哪一节负责，再按读者任务和执行顺序重写内容。
已有结构合适就局部整理；补丁积累破坏叙述时可以整页重写或重组目录，不止调整标题和措辞。
按项目规模选结构，不强制创建一套固定名称的文档。

当前使用方式、约束与尚存限制保留在易发现的位置；带日期的实施过程、计数和快照可归档，保留证据索引。
检查步骤能否连续执行：在哪里运行、需要什么状态、命令会做什么、如何判断结果、失败后从哪里继续。
若代码行为与承诺不一致，在已授权范围内修复；仅有文档授权时如实记录差异，不为统一说明而暗改代码。

## 验证与交付

- 按实际改动和仓库约定选择回归、边界验证、静态分析与格式检查。检查测试是否到达所声称的路径，并观察对外结果或必要不变量；不为可逆的低影响改动补实现镜像式测试。
- 文档核对链接、锚点、示例语法和真实参数。执行示例或测试前辨认副作用；部署、重建、登录、模型请求和对外写入不因“验证”而获得额外授权。
- 区分离线替身、真实运行、全新安装、业务验收和人工质量。不可达、超时、跳过或工具缺失按实际证据记录，不拼成安全通过或功能验收。
- 复用先前验证时核对源码、输入和环境仍一致，并说明复用范围。纯文档调整不必重新执行不相关的完整实机流程；新改动、失败或未解决疑点再触发相应复验。
- 最后核对工作区、改动范围、临时产物和受保护状态。报告已修复内容、重要保留项的理由、实际验证与剩余边界；没有修改必要时给出依据。

技能调用本身不授权提交、推送、部署或发布。当前任务已明确授权某项动作时，完成对应核验后直接执行，
不重复索要确认；本地提交和推送分别判断。要求提交全部修改时核对完整范围、暂存内容与提交后状态，
不能默认为只提交本轮文件，也不将“提交”扩展成“推送”。
